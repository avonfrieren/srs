# srs — Contexte & architecture

Mod Everest **compagnon** de [DemoJameson/Celeste.SpeedrunTool](https://github.com/DemoJameson/Celeste.SpeedrunTool) (MIT), frère de `srta` (même philosophie : dépendance + hooks, jamais de fork). But : importer la practice sheet communautaire (Google Sheets → CSV local) et colorer le temps final d'un segment du room timer selon les paliers de la sheet.
Roadmap dans `PLAN.md`. Le `README.md` sert de **changelog + instructions d'installation** — le mettre à jour à chaque feature.

## Build

- .NET 8 (`net8.0`), projet unique `srs.csproj`. Sur cette machine : `~/.dotnet/dotnet build -p:CelestePrefix="$HOME/.steam/steam/steamapps/common/Celeste"`.
- Références jeu résolues via `CelestePrefix` (auto-détecté si le repo est cloné dans `<Celeste>/Mods/xxx/`).
- **`SpeedrunTool.dll` extraite automatiquement du `SpeedrunTool.zip` officiel installé** (cible `ExtractSpeedrunToolDll`), épinglé sur **v3.27.17** dans `everest.yaml`. Pas de Publicizer pour l'instant (rien d'interne utilisé) — à ajouter comme dans srta si la phase 4 l'exige.
- Cible `OutputAsModStructure` : génère `build/` (DLL + PDB + `everest.yaml` + `Dialog/`) → à zipper en `srs.zip` dans `<Celeste>/Mods/` (comme `srta.zip`) ou copier en dossier `Mods/srs/`.

## Architecture

- `Source/SrsModule.cs` — `EverestModule` ; `Load()`/`Unload()` délèguent aux classes statiques ; `CreateModMenuSection` ajoute les entrées manuelles (bouton de mise à jour, plus tard les listes de sélection de segment — le menu auto-généré d'Everest ne sait pas faire de listes dynamiques).
- `Source/SrsSettings.cs` — settings Everest. `ASidesUrl`/`BSidesUrl` (`[SettingIgnore]` : pas dans le menu, éditables dans `Saves/modsettings-srs.celeste`) : URLs d'édition complètes des deux onglets importés, id/gid extraits par regex ; l'ancien `SheetUrl` (sheet prototype, pré-2.0.0) disparaît simplement au chargement (YamlHelper d'Everest ignore les clés inconnues). `SelectedChapter`/`SelectedCheckpoint` : sélection persistée par noms (le couple est nécessaire, les noms de checkpoints se répètent entre chapitres).
- `Source/SheetData.cs` — **pur, sans dépendance au jeu** (parseur testable) : parseur CSV RFC 4180 (guillemets, `""`, `\r\n`), parseur de temps `[hh:][mm:]ss[.fff]` (culture invariante), modèle `SheetData` → `SheetBlock` (une ligne d'en-tête = un bloc, détectée par `Hidden`+`WR` en colonnes 1-2 **ou** 2-3 → `TierStart` ; `HasCheckpoints` si la colonne 1 s'appelle `Checkpoint`) → `SheetSegment` (`Chapter` + `Name`, readonly ; le nom de chapitre n'est présent que sur la 1re ligne du groupe — cellules fusionnées — donc reporté sur les suivantes ; temps `TimeSpan?` alignés sur les colonnes depuis `TierStart`, null si cellule vide/illisible). Ne lève jamais d'exception sur contenu malformé. **`Parse(aSidesCsv, bSidesCsv)` (v2.0.0)** : parse brut des deux onglets (`ParseBlocks`, blocs sans colonne Checkpoint — « Chapter Times… » — ignorés) puis **filtre/renomme via la table `Import` hardcodée** (`(chapitre brut, checkpoint brut)` → `(chapitre mod, nom mod)`, whitelist — décision propriétaire 2026-08-05 : uniquement les checkpoints déjà supportés, pas de normalisation ; les variantes emoji 💙/📼/💎 et les lignes IL sont exclues, sauf `Depths 📼 RTM` → `Depths Tape` et `Hollows 📼 RTM` → `Hollows Tape`). Résultat : **un seul bloc fusionné** (segments dans l'ordre des lignes, onglet A puis B ⇒ les lignes B des chapitres pliés `5a/b`/`6a/b` suivent leurs lignes A comme sur l'ancienne sheet), colonnes reprises du premier onglet (les deux onglets partagent les mêmes). Adressage `(Chapter, Name)` inchangé partout ailleurs — seuls renommages visibles : `7a Start` → `0m`, ajout de `Depths Tape`.
- `Source/SheetImporter.cs` — téléchargement des **deux onglets** (HttpClient statique, timeout 20 s, **async via `Task.Run`, jamais sur le thread de jeu, jamais au lancement** ; échec de l'un = échec de la mise à jour), détection sheet privée (réponse HTML au lieu de CSV), caches `Saves/srs/asides.csv` + `bsides.csv` (écriture atomique via `.tmp` + `File.Move`), rechargés dans `Load()` ⇒ hors-ligne OK (`CacheTime` = plus récent des deux fichiers ; l'ancien `sheet.csv` pré-2.0.0 est supprimé silencieusement). Les caches **sont** aussi le fallback manuel : des CSV déposés à la main y sont relus tels quels. Entrées de menu : bouton (label muté depuis le thread worker — sûr, les items relisent leur label chaque frame) + `SubHeader` de statut. Logs sous le tag `srs`.
- `Source/SegmentSelector.cs` — sélection du checkpoint à comparer (phase 4) : `Current` (résolu par `(SelectedChapter, SelectedCheckpoint)` dans `CheckpointBlock`, null si introuvable) ; deux `TextMenu.Slider` dépendants (changer de chapitre vide et re-remplit `Values` du slider checkpoint — liste mutable, pas de reconstruction du menu ; le menu est de toute façon reconstruit à chaque ouverture, donc les données fraîchement importées apparaissent à la réouverture). À l'ouverture, les settings sont resynchronisés sur ce qui est affiché (sélection périmée ⇒ redevient valide). Chaque changement de sélection (et la resynchro d'ouverture, seulement si elle a bougé la sélection) pousse le nombre de rooms du checkpoint dans le « Number of Rooms » de SpeedrunTool via `RoomCounts.Apply`.
- `Source/SegmentAutoDetect.cs` — phase 4bis : quand `AutoDetect` (défaut on), le checkpoint joué pilote la sélection. Chapitre depuis `Session.Area` (table `ChapterMap` : ID+Mode → chapitre sheet + côté des chapitres pliés), checkpoint = dernière room de checkpoint entrée (`Everest.Events.Level.OnEnter` initialise depuis `Session.StartCheckpoint`, null = « Start » ; `OnTransitionTo` + `LevelData.HasCheckpoint` met à jour), room → nom jeu via `CheckpointData` avec `Dialog.Clean` **forcé en anglais** (clés traduites), nom jeu → nom sheet via `CheckpointMap` **hardcodée, sans normalisation** (décision propriétaire 2026-07-18, reconduite en 2.0.0 ; `7a Start` → `0m`). La room trackée est enregistrée côté save states ; la sélection est réappliquée chaque frame (couvre les loads de savestate, sans callback) et pousse `RoomCounts.Apply` à chaque bascule. Chargé **après** `TierComparison` : son hook `Level.Update` doit rester externe pour que la capture d'une complétion précède le déplacement de sélection. **Suspendu tant que `TierComparison.TimerCompleted`** : la complétion fait transitionner dans la room du checkpoint suivant, et re-cibler Number of Rooms là dé-compléterait le timer et jetterait le résultat ; la room trackée continue de suivre, la détection rattrape au reset du timer (load de savestate, clear). Les deux checkpoints cassette (`Hollows Tape` : part du checkpoint Hollows de 6A ; `Depths Tape` : part du checkpoint Depths de 5A) et la route 5A complète ne sont jamais auto-sélectionnés (ambigus/absents) — la sélection ne bouge pas.
- `Source/RoomCounts.cs` — table statique rooms-par-checkpoint (données communautaires saisies à la main, clé = `(Chapter, Name)` normalisés). `TargetFor` renvoie 99 (`Unknown`, max du slider SpeedrunTool) pour les checkpoints sans donnée (« ? » : finaux de chapitre, Granny) — le timer ne se termine alors que par la fin réelle du run (fin de chapitre, cassette, drapeau). Les deux routes cassette ont un compte (Hollows Tape = 2 ; Depths Tape = 8, route TAS `b-00→b-01→b-01b→b-02→b-11→b-13→b-17→b-22`, room de la cassette incluse — même convention que Hollows Tape) : attraper la cassette ne complète pas le room timer, seul le compte de rooms le fait. `Apply` écrit `SpeedrunToolSettings.Instance.NumberOfRooms`.
- `Source/TierComparison.cs` — phase 4 : hook `Level.Update` (après `orig`) lit `RoomTimerIsCompleted()`/`GetRoomTime()` (ModInterop, jamais le Publicizer) ; sur le front de complétion, capture le temps **seulement si `NumberOfRooms` == `RoomCounts.TargetFor(sélection)`** (sinon = practice partielle, pas de palier) — `GetRoomTime()` continue de courir après complétion, seul l'affichage de SpeedrunTool gèle. Palier recalculé chaque frame depuis le temps capturé ; `wasCompleted`/`hasCapture`/`capturedTicks` enregistrés via l'interop `SpeedrunTool.SaveLoad`. Rendu après `orig` de `SpeedrunTimerDisplay.Render` (masqué si timer Off), décalé d'une ligne si srta est chargé ; couleurs = table hex `TierColors` indexée par nom de colonne complet (le suffixe de rang compte : `Purple 1/2/3` = 3 teintes distinctes ; WR/Hidden blanc, Unranked gris, inconnu → blanc). Hotkey `ToggleShowTier` (phase 5) gérée dans le même hook, popup on/off via `PopupMessageUtils` de SpeedrunTool (classe publique, pas de Publicizer).
- `Dialog/English.txt` + `French.txt` — `MODOPTIONS_SRS_TITLE` (titre du menu auto) et clés `SRS_*` (entrées manuelles). Pas de placeholders `{0}` dans les dialogs (Celeste peut interpréter les accolades) : composer en code.

- `Unranked` : colonne sans valeurs (palier « au-delà de Red 3 »). `Hidden` : `0:00.000` partout. Certains WR valent `0:00.000` (ex. `Depths`) — ignorés par la comparaison (`threshold > TimeSpan.Zero`). Cellules `#REF!` possibles dans les blocs Chapter Times (non importés) ⇒ null de toute façon.
- Sémantique de comparaison : premier seuil ≥ temps réalisé ⇒ palier atteint.

## Repères SpeedrunTool (pour les phases 3-4)

- ModInterop `SpeedrunTool.RoomTimer` : `RoomTimerIsCompleted()`, `GetRoomTime()` — suffisant pour comparer un temps final ; préférer l'interop au Publicizer (stable entre releases ; DemoJameson accepte des ajouts sur demande Discord).
- ModInterop `SpeedrunTool.SaveLoad` : tout état statique muté en gameplay doit y être enregistré (`RegisterStaticTypes`) sous peine de desync des save states.
- HUD : dessiner après `orig` de `On.Celeste.SpeedrunTimerDisplay.Render` (srs charge après SpeedrunTool ⇒ ses hooks enveloppent les siens) — voir `RoomDeltas.cs` de srta pour le modèle.
